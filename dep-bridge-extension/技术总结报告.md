# 站存-发车流程填表桥 · 技术总结报告

> 目标：把「股道存车计算器」页面里点「编好 / 发送」得到的填表数据
> （**股道 / 编组车次 / 辆数 / 换长 / 尾车车号** → 报表的 `B4~F4` 单元格）
> 自动写进「发车作业报表」页面，要求：
>
> 1. **跨标签页、跨域**可用（计算器与报表常不在同一个域）；
> 2. 必须是**真写入**——写进帆软的数据模型，让报表**提交时能通过校验**；
> 3. 两种挂载形态都要支持：报表页**嵌在帆软平台页的 iframe 里**，以及**直接打开报表页本身**。

---

## 一、最终结论

| 验证项 | 环境 | 结果 |
|---|---|---|
| 报表页以 iframe 挂载在平台页内 | 本地测试页 `test-fs-platform.html` | ✅ 7 个定位策略全部 `ok=5`（验证后已精简为 2 个按钮，见 §3.4） |
| 直接打开报表页（无平台外壳） | 本地 `departure_flow.html` | ✅ `ok=5 target=self(本页即报表页)` |
| 同上两种场景 | **内网实机** | ✅ 均已发送成功 |

核心实现：**由扩展的 background 用 `chrome.scripting.executeScript` 把填表函数注入到报表页的 `MAIN` world 执行，函数内用帆软官方的 `contentPane.setCellValue()` 写值，返回值直接带回计算器页。**

## 二、为什么重构：旧链路的「5 跳」太脆

### 2.1 旧链路

```
计算器页(app.js)
  └─ window.postMessage ─→ content.js(ISOLATED) ─→ background.js
                                                       │
                          ┌────────────────────────────┘
                          ▼
                    报表标签页 content.js(ISOLATED)
                          └─ window.postMessage ─→ page-fill.js(MAIN)
                                                       └─ 找 iframe.contentPane → setCellValue
```

### 2.2 问题

1. **链路太长**：任何一跳出问题（世界隔离、`ev.source` 判定、`tabs.sendMessage` 投递失败、注入时机），
   结果都是**静默失败**——计算器页显示「已下发填报指令」，然后**没有任何回执**，无从定位。
2. **依赖常驻脚本**：报表页必须已注入 `page-fill.js`；若扩展是后装的、或页面先于扩展打开，就收不到指令。
3. **回执要再走 3 跳**回来，且多个 frame 都会回执，互相覆盖（见 §5-坑 4）。

### 2.3 新链路（本次重构）

```
计算器页(app.js)
  └─ window.postMessage ─→ content.js(ISOLATED) ─→ background.js
                                                       │
                                     chrome.scripting.executeScript({
                                       target: { tabId, allFrames: true },
                                       world:  'MAIN',
                                       func:   depFillFunc,      ← 自包含函数，被序列化注入
                                       args:   [cells, strategy]
                                     }) ─→ 每个 frame 各跑一次，返回值直接带回
                                                       │
                                     ┌─────────────────┘
                                     ▼
                            取「ok 最大」的 frame 结果 → 回执给计算器页
```

**收益**：链路 **5 跳 → 1 跳**；不再依赖常驻脚本；每个 frame 的结果**直接可观测**。

## 三、关键技术决策（逐个说明"为什么"）

### 3.1 为什么必须 `world: "MAIN"`

帆软报表的 `contentPane` 是**页面自身的运行时对象**（`window.contentPane`），
它挂在**页面的 JS 环境**里。而扩展默认的 content script 跑在 **ISOLATED world**——
两个世界**共享 DOM 但不共享 JS 变量**，隔离世界读不到 `window.contentPane`。

> 所以 `depFillFunc` 必须注入 `MAIN` world，才能：
> ```
> iframe.contentWindow.contentPane.setCellValue(id, null, value)
> ```

### 3.2 为什么用 `func` 而非 `files` / `eval`

| 方式 | 说明 | 结论 |
|---|---|---|
| `files: ['x.js']` | 注入脚本文件 | 需额外打包，且不方便带回返回值 |
| `func: fn` | Chrome 自动 `toString()` 序列化函数 | ✅ **采用**；返回值直接可取 |
| 字符串 + `eval` | 把代码当字符串执行 | ❌ MAIN world 受**页面 CSP** 约束，帆软页若禁 `unsafe-eval` 就失败 |

**代价**：`func` 函数**不能引用外部作用域变量**（序列化后外部变量不存在），
所以 `depFillFunc` 是**完全自包含**的——选择器表、`paneWin` / `probe` / `writeInto` 全部写在函数体内。

### 3.3 `allFrames: true` + 「每个 frame 自判」

报表可能在**多层 frame**里。与其在顶层猜，不如：

> **往该标签页的所有 frame 都注入，每个 frame 自己回答"我这层能不能找到 contentPane"。**

- 找到 → 写并返回 `{ok:5, target:'...'}`；
- 找不到 → 返回 `{ok:0, skip:true}`（由 background 忽略，**不会覆盖成功回执**）。

最后 background 取 **`ok` 最大**的那个结果作回执——所以"外层找不到、内嵌层找到"也能正确命中。

### 3.4 三级定位（覆盖率的关键）

`depFillFunc` 里按顺序尝试：

```
① self       本帧自己有 contentPane          → 直接写本帧
② 选择器找 iframe（7 种策略各查一组）
             .fs-tab-content-item.fs-tab-content-toolbar   ← 首选（实测最准）
             iframe.fs-tab-content-toolbar
             iframe[id^="fs_tab"] / iframe[name^="fs_tab"]
             .fs-tab-content-item
             iframe                                        ← 兜底
             （命中的若是「容器元素」，会自动在其内部一层再找 iframe）
③ 本帧兜底    都没找到，但本帧自带 contentPane  → 写本帧
             （= 直接打开报表页、没有平台外壳的场景）
```

> **UI 已精简为 2 个模式**（7 个全部验证可用后做的减法）：
>
> | 按钮 | strategy | 覆盖场景 |
> |---|---|---|
> | ① 平台页 / 报表 iframe | `fs_tab_toolbar` | 报表挂在平台页 iframe 里；**一个策略内含多级备用选择器**，等于原来的 `fs_tab_toolbar` + `fs_tab_id` + `fs_tab_class` + `name_fs_tab` + `first_iframe` + `all` 之和 |
> | ② 直接打开报表页 | `self` | 不经平台外壳、直接打开报表页本身 |
>
> 未知/历史 strategy 值（`all`、`fs_tab_id` 等）**一律按 ① 处理**，向后兼容。
> 之所以能这样合并：7 个策略最终命中的都是**同一个真报表 iframe**，
> 差别只在"用哪个选择器找到它"——把选择器做成**有序备用链**，一个按钮就够了。

### 3.5 只用 `contentPane.setCellValue`，**不保留 DOM 降级**

旧实现里有一条"纯 DOM 降级"：

```js
// 旧：找不到 contentPane 就直接改 DOM
td.innerHTML = '';
var d = document.createElement('div');
d.textContent = val;
```

**这条必须删掉**，因为它只改**显示**，报表的**数据模型不知道** → 提交时值丢失 / 校验不过。
新实现**没有降级路径**：拿不到 `contentPane` 就返回 `ok:0`，**绝不假装成功**。

> 另有一层保险：候选 iframe 必须先通过 `typeof cp.setCellValue === 'function'` 校验，
> 才算"有效目标"（`paneWin()`），避免把普通 iframe 当成报表。

### 3.6 目标标签页怎么选

| 步骤 | 规则 |
|---|---|
| ① 精确匹配 | `isReport(tab.url)`：**同 host + 同 pathname** 命中 popup 里配置的「报表地址」 |
| ② 广播兜底 | 一个都没匹配、且开关为**开**（默认开）→ 注入**所有普通标签页**（跳过 `chrome://` `file://` 等） |
| ③ 无关页面 | 由 `depFillFunc` 自己判断"没有 contentPane"→ 返回 `skip`，不产生副作用 |

> **为什么要兜底**：`isReport` 是**单一 URL 精确匹配**。当"平台页"和"直接打开的报表页"
> 两种用法并存时，popup 里只能填一个地址，另一种必然匹配不上——只能靠广播覆盖。
> **所以生产上建议保持兜底开启。**

### 3.7 多 frame 回执聚合：「成功优先」

一次发送会收到**多个 frame** 的回执。若直接逐条展示，**后到的失败回执会把成功提示覆盖成「编好失败」**。

计算器页因此改为**窗口聚合**：

```js
// 保留 ok 最大的结果；全成功立即展示，否则等 900ms 窗口结束再展示
if (!depFillBest || ok > depFillBest.ok) depFillBest = { ok, error, failed };
if (ok >= 5) { clearTimeout(depFillTimer); showFillResult(depFillBest); }
```

## 四、踩坑记录（现象 → 根因 → 修复）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 7 个发送模式在正式环境**全部失败** | 所有定位策略都被 **`window === window.top`** 硬限制。帆软平台页把报表 iframe 嵌在中间层 frame 时：顶层 `document` 找不到，**中间层找得到却被 `isSkip` 跳过** | 去掉 top 限制，改为"**谁在自己的 document 里找得到，谁就负责写**"（找到的 frame 唯一，不会重复） |
| 2 | 按 `.fs-tab-content-item.fs-tab-content-toolbar` 定位不到 | 旧代码只试**带 `iframe.` 前缀**的选择器；且该选择器命中的可能是**容器元素** | 首选**无前缀**的实测选择器；`trySelect` 增加"**容器内一层 iframe**"探测 |
| 3 | 填表静默失败、无法定位 | 消息转发 **5 跳**，任一环断了都无声 | 改 `executeScript` 注入（**1 跳**），每个 frame 返回值直接带回 |
| 4 | 明明写成功了，界面却显示「编好失败」 | 多个 frame 都回传 `filled`，**失败回执后到，覆盖了成功提示** | 回执改「**成功优先 + 900ms 窗口聚合**」 |
| 5 | 计算器页也报「没找到目标」，误导排查 | 计算器页改用 `http://` 打开后**不再是 `file://`**，于是被兜底广播扫到；它自带 `<iframe id="mapFrame">` → 通过了"有 iframe"检查 | `page-fill.js` 检测计算器页独有元素（`#btnSendCurrent` / `#detailTable`）→ **直接静默返回** |
| 6 | **直接打开报表页**时，一个值都写不进去 | ① 前置过滤「本帧无 iframe 就跳过」把它**误杀**；② 缺少"本帧即报表页"的兜底 | ① 前置过滤放行「**本帧自带 contentPane**」；② 三级定位增加 ③ 本帧兜底 |
| 7 | 地图数据接口（`getMapDftPoint` / `getMapDlnPoint` / `getJl` 等）始终用旧版本 `C260702`，即使 `getReleaseVersionData` 返回了新版本 `C260802` | **时序竞态**：`GetToken` 成功后同步调用 `getVersion()`（异步）紧接着 `firePendingMapLoad()` → `loadMapData` 立刻发请求，此刻 `map_version` 还是 `null`，后端收到空版本号退回默认旧版本 | `loadMapData` 在 `map_version` 就绪前挂起等待；并加防重入 `window.__mapDataLoaded`，避免二次加载把早发的空版本请求"算数" |
| 8 | 面板点「保存 Token」报 `Failed to fetch`，而「测试请求」却成功 | 保存 Token 走 `fetchMapToken()` 用的是**内存里的 `mapTokenCfg`**；面板改了 URL / Referer 并 `chrome.storage.local.set` 保存后，**内存配置没同步刷新**，于是请求用了旧地址 / 空 Referer | ① `fetchMapToken` 支持从消息直接收 `{url, referer}`；② 保存时把面板当前输入一并发给 background；③ `storage.onChanged` 监听 `depTokenUrl` / `depTokenReferer`，保存后立刻 `loadCfg()` 刷新内存配置 |

> 坑 5 的诊断过程值得记一笔：那条"失败"日志里其实**自带答案**——
> `本 frame=http://.../HTML/index.html`。**先看日志里的 URL，再判断是哪一页在抱怨。**

## 六、已知限制与后续

1. **跨域（唯一的硬限制）**
   若生产报表 iframe 与平台页**不同源**，浏览器不允许读 `iframe.contentWindow.contentPane`，
   任何方案都无法绕过。
   → **"直接打开报表页"没有这个问题**（自己就是报表页），生产上这可能是最稳的路径。

2. **未做「填完自动提交」**
   当前只写入不提交。若需要，在 `depFillFunc` 的写入循环后追加提交调用即可
   （需提供提交方式，如 `contentPane.commit()` 或某个按钮的 id）。

3. **报表地址为单一 URL 精确匹配**
   "平台页 + 直接打开报表页"并存时靠**广播兜底**覆盖；如只想要精确控制，可在 popup 里关掉兜底。

4. **`ok=5` 的含义**
   仅代表 5 个单元格**调用 `setCellValue` 未抛错**；是否被后端接受仍取决于报表模板与业务校验。

## 七、文件职责与数据流

| 文件 | 职责 |
|---|---|
| `manifest.json` | MV3 清单。两段 content script：`content.js`（ISOLATED / `document_start` / all_frames）+ `page-fill.js`（**MAIN** / `document_idle` / all_frames）；权限 `tabs/scripting/storage/alarms/declarativeNetRequest` |
| `background.js` | ① **发车填表**：`depFillFunc` + `fillByExecute()`（executeScript 注入）；② 目标标签页选取与回执；③ **地图 API 代理**（`proxyMapApi` 绕 CORS / Referer，`fetchMapToken(opts)` 取 token，支持从消息收 `{url,referer}` 立即生效）；④ **面板测试** `testTokenAndVersion`（取 token 再取版本号）；⑤ 工具栏图标状态；⑥ `reloadReport` 刷新报表页。**`storage.onChanged` 监听 `depTokenUrl`/`depTokenReferer` 刷新内存 `mapTokenCfg`** |
| `content.js` | ISOLATED world 消息桥：页面 `postMessage` ↔ `chrome.runtime`。**只转发，不碰页面逻辑** |
| `page-fill.js` | MAIN world 常驻：**车次列表回传**、地图 token 落地、**后备填表**（与 `depFillFunc` 同一套定位逻辑） |
| `popup.html / popup.js` | 配置界面：**标签式切换（发车流程 / 地图管理）**、报表地址、**广播兜底开关**、地图 Token 地址 / Referer（默认 `10.208.2.72:8080` + 测试 `localhost:3000` 按钮、Referer 默认按钮）、**测试请求**（取 token + 版本号，两行显示 `Token：`/`版本号：`）、**保存 Token**（仅提示 `✓ 已保存到本地`）、主题 |
| `rules.json` | DNR 规则：给地图后端接口补 CORS 响应头 / Referer |
| `安装说明.md` | 安装步骤与**排查手册** |

### 数据流（发车填表）

```
[计算器页] 点「发送」
   │  window.postMessage({channel:'__DEP_BRIDGE__', type:'fillByStrategy', cells, strategy})
   ▼
[content.js · ISOLATED]  转发
   │  chrome.runtime.sendMessage
   ▼
[background.js]  选目标标签页（精确匹配 → 广播兜底）
   │  chrome.scripting.executeScript({tabId, allFrames, world:'MAIN', func:depFillFunc, args})
   ▼
[报表页各 frame · MAIN]  depFillFunc 执行
   │  ①self ②找 iframe ③本帧兜底  →  contentPane.setCellValue(id, null, val)
   ▼
[background.js]  取 ok 最大的 frame 结果
   │  tabs.sendMessage → content.js → window.postMessage
   ▼
[计算器页]  成功优先 + 窗口聚合 → 状态栏提示「X道 编好」
```

看**报表标签页**（以及被兜底广播扫到的页面）的 F12 控制台，按 `[dep-bridge]` 过滤：

| 日志 | 含义 / 处理 |
|---|---|
| `注入完成：ok=5 target=...` | ✅ 成功 |
| `target=self(本页即报表页)` | ✅ 直接打开报表页时的正常命中 |
| `本 frame 的 iframe 里没有 contentPane（…请刷新报表页后重试）` | 报表未渲染完 → 刷新报表页后重试 |
| `未匹配报表页，兜底注入所有普通标签页（N 个）` | popup 的「报表地址」与实际不符（可依赖兜底，或改成实际地址） |
| `未找到报表标签页` | 报表页没开，或地址不匹配且**兜底已关** |
| `注入失败 tab N: Cannot access contents of the page` | 该页不允许注入（`chrome://`、商店页等） |
| `⨯ 本 frame 有 iframe，但没有带 contentPane 的帆软报表：… 本 frame=<URL>` | **先看 URL**：若不是报表页，属正常（兜底广播打扰）；若是报表页，多为未加载完 |
| **完全没有 ok、`contentPane` 读不到** | ⚠️ 大概率**跨域**（iframe 与平台页不同源） |

**改过扩展代码后，必须**：`chrome://extensions/` → 本扩展 → 点「刷新」→ 再刷新相关页面。

## 九、可复用的经验

1. **注入 > 转发**：扩展与页面通信，能"一次注入拿返回值"就别搭多跳消息链——跳数越多，静默失败越难查。
2. **让每个执行单元自判角色**：`allFrames` 注入 + 每帧自答"我能不能干"，比在顶层猜结构稳得多。
3. **不要用 DOM 伪造数据**：对"会被提交/校验"的数据，必须走官方运行时 API；DOM 降级只会制造"看起来成功"的假象。
4. **回执要设计去重/优先级**：多执行单元并发回执时，必须定义"谁的结果算数"。
5. **日志里带上身份**：把 `location.href` / frame 角色打进日志，能省掉大量排查时间（坑 5 就是靠它破的）。

## 十、地图 Token 代理与请求转发（线上模式）

> 地图页 `chinamap.html` 以 `file://` 打开（`origin = null`），直接 `fetch` 内网后端
> `http://10.208.2.72:8080` 会被浏览器 CORS 拦截。本扩展用 **background 代发 + 补请求头** 解决，
> 让地图在**在线模式**下也能正常加载（站存点、交路、节点等数据）。

### 10.1 转发链路（全链路）

```
地图页 chinamap.html (file://，origin=null)
  └─ GetToken() → /getToken                 （扩展代发，带 Referer）
       └─ getVersion() → /getReleaseVersionData（带 Authorization）→ 写入全局 map_version
            └─ initMap() → loadMapData()
                 ├─ /getMapDftPoint    (map_version)
                 ├─ /getMapDlnPoint    (map_version)
                 ├─ /getMapDndPoint    (map_version)
                 ├─ /getMidStationByLj (map_version, lj)
                 ├─ /getNode           (map_version, id)
                 └─ /getJl             (map_version, 发站…)
        ↓ 全部经 $.ajax
map-api-proxy.js  (覆盖 $.ajax，匹配白名单 API_PATHS)
        ↓ postMessage(__DEP_BRIDGE__)
content.js (ISOLATED) → chrome.runtime
        ↓
background.js  proxyMapApi → fetch(base + path ? data, { Authorization, Referer })
        ↓ send(map-api-result)
content.js → postMessage 回页面 → map-api-proxy 恢复 jQuery success/error
```

- 白名单（`API_PATHS`）：`/getToken` `/getReleaseVersionData` `/getMapDftPoint` `/getMapDlnPoint`
  `/getMapDndPoint` `/getMidStationByLj` `/getNode` `/getJl`。页面其余脚本（如 `search.js` 站名搜索）走本地数据，不发起网络请求。
- `ajaxPrefilter` 负责把相对路径前缀成 `getApiBase()`；代理自身用 `getApiBase() + pathOf(url)` 重算 base，两者一致。
- 回环用 `__from: 'dep-bridge-content'` 标记断开；`background.js` 用 `isMapFrame` 仅放行 `chinamap.html` 发起的代理请求。

### 10.2 版本号时序竞态（核心 bug，见坑 7）

- **现象**：`getToken` / `getReleaseVersionData` 成功（返回 `C260802`），但 `getMapDftPoint` 等接口拿到的还是旧版本 `C260702`。
- **根因**：请求里用的全是全局变量 `map_version`，**不是写死**。但 `getVersion()` 是异步的，而 `GetToken` 成功后**同步**紧跟着 `firePendingMapLoad()` → `loadMapData` 立刻发请求，此时 `map_version` 还是 `null`，后端收空版本号退回默认旧版本。后到的 `initMap` 二次加载虽有正确版本，但无防重入，"早发的空版本请求"反而先生效。
- **修复**（`HTML/Map/js/map.js`）：
  1. `loadMapData()` 增加 `if (map_version == null) { window.__pendingMapLoad = loadMapData; return; }` —— 版本号没就绪前**挂起等待**；
  2. 增加 `window.__mapDataLoaded` 防重入，避免重复加载互相覆盖；
  3. `firePendingMapLoad()` 在 `__pendingMapLoad` 为 `undefined` 时安全空转（不再 `fn()` 抛错）。

### 10.3 Referer / URL 同步（保存 Token 失败，见坑 8）

- **现象**：点「保存 Token」报 `Failed to fetch`，而「测试请求」成功。
- **根因**：保存 Token 走 `fetchMapToken()`，它读**内存** `mapTokenCfg.url/referer`；面板改了地址后只是 `chrome.storage.local.set` 落盘，但**内存配置没刷新**，于是用了旧地址 / 空 Referer。而「测试请求」直接把面板当前 URL/Referer 传给 `fetch()`，所以成功。
- **修复**（`background.js` + `popup.js`）：
  1. `fetchMapToken(opts, cb)` 支持从消息收 `{url, referer}`，优先用消息里的值，否则退回 `mapTokenCfg`；
  2. popup 点「保存 Token」时把 `tokenUrl.value` / `tokenReferer.value` 一起 `sendMessage` 过去；
  3. `chrome.storage.onChanged` 监听 `depTokenUrl` / `depTokenReferer`，保存后立刻 `loadCfg()` 刷新内存配置（内部 `map-need-token` 也用最新值）。

### 10.4 面板 UI（地图管理标签）

- **标签式切换**：顶部 `发车流程 | 地图管理` 两个标签，点击切换面板，不再上下堆叠。
- **Token 地址**：默认按钮填 `http://10.208.2.72:8080/getToken?ip=10.208.2.72`；「测试」按钮填 `http://localhost:3000/getToken?ip=10.208.2.72`；打开即预填默认值，可手改。
- **Referer**：默认按钮填 `http://10.208.2.72:8080/cljl`。
- **测试请求**：走 `testTokenAndVersion` —— 先用当前 URL/Referer 取 token，再用该 token 请求 `/getReleaseVersionData` 取版本号，两行显示：
  ```
  Token：   eyJ0eXAiOiJKV1QiLCJhbGciOiJIUzI1NiJ9.ey…
  版本号：  C260802
  ```
- **保存 Token**：成功后 `Token：` 行只显示 `✓ 已保存到本地`（不再打印 token 内容）。

### 10.5 验证结果

- 内网实机：`getToken`、`getReleaseVersionData`、`getMapDftPoint` / `getMapDlnPoint` / `getJl` 等均成功，数据请求带**最新版本号** `C260802`。
- 接口白名单核对：页面所有 `$.ajax` 端点全部在 `API_PATHS` 内，`search.js` 不联网，**无漏网接口**在线上模式绕开代理导致 CORS 失败。
- `manifest.json` 权限：`host_permissions` 含 `http://10.208.2.72:8080/*` 与 `<all_urls>`，并带 `declarativeNetRequest` + `rules.json`（给后端补 Referer）。

### 10.6 ⚠️ 使用前提（避免"线上不能用"）

地图后端地址与面板 Token 地址是**两套独立配置**，必须指向同一后端：

1. **地图页「后端地址」下拉（`localStorage: mapApiBase`）** 默认是 `http://localhost:3000`，线上必须改成
   **`http://10.208.2.72:8080`**；否则地图请求仍打 localhost，失败后才退回本地兜底数据。
2. 面板里 **`Token 地址 = http://10.208.2.72:8080/getToken?ip=10.208.2.72`**、
   **`Referer = http://10.208.2.72:8080/cljl`**。

两套都配成 `10.208.2.72:8080` 后，线上模式即正常。

### 10.7 调试要点（地图）

- F12 控制台按 `[dep-bridge]` 过滤；地图请求是否带正确版本号，看 `getMapDftPoint` 实际发出的 query 里 `map_version` 值。
- 点「测试请求」能成功、点「保存 Token」失败 → 通常是 Referer / URL 未同步（已按 §10.3 修）；若两者都失败，先确认 `mapApiBase` 下拉是否仍是 `localhost:3000`（§10.6）。
- 改过扩展代码后务必：`chrome://extensions/` → 本扩展 → 点「刷新」→ 再刷新地图页。

## 十一、可复用的经验（续）

6. **异步结果别和同步触发竞跑**："先发起请求、再用响应配置下一批请求"时，务必让下一批**等响应就绪**（挂起/回调里触发），否则就会像坑 7 那样用旧配置发出去。
7. **消息配置与内存状态要同步**：面板保存的只是 `chrome.storage`，background 里的内存配置（`mapTokenCfg` 之类）必须显式 `loadCfg()`/`reload`，否则"面板改了、运行态没改"，表现为"测试能过、正式失败"。
