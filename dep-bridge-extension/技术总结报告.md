# 站存-发车流程填表桥 · 技术总结报告

> 目标：把「股道存车计算器」页面里点「编好 / 发送」得到的填表数据
> （**股道 / 编组车次 / 辆数 / 换长 / 尾车车号** → 报表的 `B4~F4` 单元格）
> 自动写进「发车作业报表」页面，要求：
>
> 1. **跨标签页、跨域**可用（计算器与报表常不在同一个域）；
> 2. 必须是**真写入**——写进帆软的数据模型，让报表**提交时能通过校验**；
> 3. 两种挂载形态都要支持：报表页**嵌在帆软平台页的 iframe 里**，以及**直接打开报表页本身**。

---

## 一、最终结论

| 验证项 | 环境 | 结果 |
|---|---|---|
| 报表页以 iframe 挂载在平台页内 | 本地测试页 `test-fs-platform.html` | ✅ 7 个定位策略全部 `ok=5`（验证后已精简为 2 个按钮，见 §3.4） |
| 直接打开报表页（无平台外壳） | 本地 `departure_flow.html` | ✅ `ok=5 target=self(本页即报表页)` |
| 同上两种场景 | **内网实机** | ✅ 均已发送成功 |

核心实现：**由扩展的 background 用 `chrome.scripting.executeScript` 把填表函数注入到报表页的 `MAIN` world 执行，函数内用帆软官方的 `contentPane.setCellValue()` 写值，返回值直接带回计算器页。**

## 二、为什么重构：旧链路的「5 跳」太脆

### 2.1 旧链路

```
计算器页(app.js)
  └─ window.postMessage ─→ content.js(ISOLATED) ─→ background.js
                                                       │
                          ┌────────────────────────────┘
                          ▼
                    报表标签页 content.js(ISOLATED)
                          └─ window.postMessage ─→ page-fill.js(MAIN)
                                                       └─ 找 iframe.contentPane → setCellValue
```

### 2.2 问题

1. **链路太长**：任何一跳出问题（世界隔离、`ev.source` 判定、`tabs.sendMessage` 投递失败、注入时机），
   结果都是**静默失败**——计算器页显示「已下发填报指令」，然后**没有任何回执**，无从定位。
2. **依赖常驻脚本**：报表页必须已注入 `page-fill.js`；若扩展是后装的、或页面先于扩展打开，就收不到指令。
3. **回执要再走 3 跳**回来，且多个 frame 都会回执，互相覆盖（见 §5-坑 4）。

### 2.3 新链路（本次重构）

```
计算器页(app.js)
  └─ window.postMessage ─→ content.js(ISOLATED) ─→ background.js
                                                       │
                                     chrome.scripting.executeScript({
                                       target: { tabId, allFrames: true },
                                       world:  'MAIN',
                                       func:   depFillFunc,      ← 自包含函数，被序列化注入
                                       args:   [cells, strategy]
                                     }) ─→ 每个 frame 各跑一次，返回值直接带回
                                                       │
                                     ┌─────────────────┘
                                     ▼
                            取「ok 最大」的 frame 结果 → 回执给计算器页
```

**收益**：链路 **5 跳 → 1 跳**；不再依赖常驻脚本；每个 frame 的结果**直接可观测**。

## 三、关键技术决策（逐个说明"为什么"）

### 3.1 为什么必须 `world: "MAIN"`

帆软报表的 `contentPane` 是**页面自身的运行时对象**（`window.contentPane`），
它挂在**页面的 JS 环境**里。而扩展默认的 content script 跑在 **ISOLATED world**——
两个世界**共享 DOM 但不共享 JS 变量**，隔离世界读不到 `window.contentPane`。

> 所以 `depFillFunc` 必须注入 `MAIN` world，才能：
> ```
> iframe.contentWindow.contentPane.setCellValue(id, null, value)
> ```

### 3.2 为什么用 `func` 而非 `files` / `eval`

| 方式 | 说明 | 结论 |
|---|---|---|
| `files: ['x.js']` | 注入脚本文件 | 需额外打包，且不方便带回返回值 |
| `func: fn` | Chrome 自动 `toString()` 序列化函数 | ✅ **采用**；返回值直接可取 |
| 字符串 + `eval` | 把代码当字符串执行 | ❌ MAIN world 受**页面 CSP** 约束，帆软页若禁 `unsafe-eval` 就失败 |

**代价**：`func` 函数**不能引用外部作用域变量**（序列化后外部变量不存在），
所以 `depFillFunc` 是**完全自包含**的——选择器表、`paneWin` / `probe` / `writeInto` 全部写在函数体内。

### 3.3 `allFrames: true` + 「每个 frame 自判」

报表可能在**多层 frame**里。与其在顶层猜，不如：

> **往该标签页的所有 frame 都注入，每个 frame 自己回答"我这层能不能找到 contentPane"。**

- 找到 → 写并返回 `{ok:5, target:'...'}`；
- 找不到 → 返回 `{ok:0, skip:true}`（由 background 忽略，**不会覆盖成功回执**）。

最后 background 取 **`ok` 最大**的那个结果作回执——所以"外层找不到、内嵌层找到"也能正确命中。

### 3.4 三级定位（覆盖率的关键）

`depFillFunc` 里按顺序尝试：

```
① self       本帧自己有 contentPane          → 直接写本帧
② 选择器找 iframe（7 种策略各查一组）
             .fs-tab-content-item.fs-tab-content-toolbar   ← 首选（实测最准）
             iframe.fs-tab-content-toolbar
             iframe[id^="fs_tab"] / iframe[name^="fs_tab"]
             .fs-tab-content-item
             iframe                                        ← 兜底
             （命中的若是「容器元素」，会自动在其内部一层再找 iframe）
③ 本帧兜底    都没找到，但本帧自带 contentPane  → 写本帧
             （= 直接打开报表页、没有平台外壳的场景）
```

> **UI 已精简为 2 个模式**（7 个全部验证可用后做的减法）：
>
> | 按钮 | strategy | 覆盖场景 |
> |---|---|---|
> | ① 平台页 / 报表 iframe | `fs_tab_toolbar` | 报表挂在平台页 iframe 里；**一个策略内含多级备用选择器**，等于原来的 `fs_tab_toolbar` + `fs_tab_id` + `fs_tab_class` + `name_fs_tab` + `first_iframe` + `all` 之和 |
> | ② 直接打开报表页 | `self` | 不经平台外壳、直接打开报表页本身 |
>
> 未知/历史 strategy 值（`all`、`fs_tab_id` 等）**一律按 ① 处理**，向后兼容。
> 之所以能这样合并：7 个策略最终命中的都是**同一个真报表 iframe**，
> 差别只在"用哪个选择器找到它"——把选择器做成**有序备用链**，一个按钮就够了。

### 3.5 只用 `contentPane.setCellValue`，**不保留 DOM 降级**

旧实现里有一条"纯 DOM 降级"：

```js
// 旧：找不到 contentPane 就直接改 DOM
td.innerHTML = '';
var d = document.createElement('div');
d.textContent = val;
```

**这条必须删掉**，因为它只改**显示**，报表的**数据模型不知道** → 提交时值丢失 / 校验不过。
新实现**没有降级路径**：拿不到 `contentPane` 就返回 `ok:0`，**绝不假装成功**。

> 另有一层保险：候选 iframe 必须先通过 `typeof cp.setCellValue === 'function'` 校验，
> 才算"有效目标"（`paneWin()`），避免把普通 iframe 当成报表。

### 3.6 目标标签页怎么选

| 步骤 | 规则 |
|---|---|
| ① 精确匹配 | `isReport(tab.url)`：**同 host + 同 pathname** 命中 popup 里配置的「报表地址」 |
| ② 广播兜底 | 一个都没匹配、且开关为**开**（默认开）→ 注入**所有普通标签页**（跳过 `chrome://` `file://` 等） |
| ③ 无关页面 | 由 `depFillFunc` 自己判断"没有 contentPane"→ 返回 `skip`，不产生副作用 |

> **为什么要兜底**：`isReport` 是**单一 URL 精确匹配**。当"平台页"和"直接打开的报表页"
> 两种用法并存时，popup 里只能填一个地址，另一种必然匹配不上——只能靠广播覆盖。
> **所以生产上建议保持兜底开启。**

### 3.7 多 frame 回执聚合：「成功优先」

一次发送会收到**多个 frame** 的回执。若直接逐条展示，**后到的失败回执会把成功提示覆盖成「编好失败」**。

计算器页因此改为**窗口聚合**：

```js
// 保留 ok 最大的结果；全成功立即展示，否则等 900ms 窗口结束再展示
if (!depFillBest || ok > depFillBest.ok) depFillBest = { ok, error, failed };
if (ok >= 5) { clearTimeout(depFillTimer); showFillResult(depFillBest); }
```

## 四、踩坑记录（现象 → 根因 → 修复）

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 7 个发送模式在正式环境**全部失败** | 所有定位策略都被 **`window === window.top`** 硬限制。帆软平台页把报表 iframe 嵌在中间层 frame 时：顶层 `document` 找不到，**中间层找得到却被 `isSkip` 跳过** | 去掉 top 限制，改为"**谁在自己的 document 里找得到，谁就负责写**"（找到的 frame 唯一，不会重复） |
| 2 | 按 `.fs-tab-content-item.fs-tab-content-toolbar` 定位不到 | 旧代码只试**带 `iframe.` 前缀**的选择器；且该选择器命中的可能是**容器元素** | 首选**无前缀**的实测选择器；`trySelect` 增加"**容器内一层 iframe**"探测 |
| 3 | 填表静默失败、无法定位 | 消息转发 **5 跳**，任一环断了都无声 | 改 `executeScript` 注入（**1 跳**），每个 frame 返回值直接带回 |
| 4 | 明明写成功了，界面却显示「编好失败」 | 多个 frame 都回传 `filled`，**失败回执后到，覆盖了成功提示** | 回执改「**成功优先 + 900ms 窗口聚合**」 |
| 5 | 计算器页也报「没找到目标」，误导排查 | 计算器页改用 `http://` 打开后**不再是 `file://`**，于是被兜底广播扫到；它自带 `<iframe id="mapFrame">` → 通过了"有 iframe"检查 | `page-fill.js` 检测计算器页独有元素（`#btnSendCurrent` / `#detailTable`）→ **直接静默返回** |
| 6 | **直接打开报表页**时，一个值都写不进去 | ① 前置过滤「本帧无 iframe 就跳过」把它**误杀**；② 缺少"本帧即报表页"的兜底 | ① 前置过滤放行「**本帧自带 contentPane**」；② 三级定位增加 ③ 本帧兜底 |

> 坑 5 的诊断过程值得记一笔：那条"失败"日志里其实**自带答案**——
> `本 frame=http://.../HTML/index.html`。**先看日志里的 URL，再判断是哪一页在抱怨。**

## 六、已知限制与后续

1. **跨域（唯一的硬限制）**
   若生产报表 iframe 与平台页**不同源**，浏览器不允许读 `iframe.contentWindow.contentPane`，
   任何方案都无法绕过。
   → **"直接打开报表页"没有这个问题**（自己就是报表页），生产上这可能是最稳的路径。

2. **未做「填完自动提交」**
   当前只写入不提交。若需要，在 `depFillFunc` 的写入循环后追加提交调用即可
   （需提供提交方式，如 `contentPane.commit()` 或某个按钮的 id）。

3. **报表地址为单一 URL 精确匹配**
   "平台页 + 直接打开报表页"并存时靠**广播兜底**覆盖；如只想要精确控制，可在 popup 里关掉兜底。

4. **`ok=5` 的含义**
   仅代表 5 个单元格**调用 `setCellValue` 未抛错**；是否被后端接受仍取决于报表模板与业务校验。

## 七、文件职责与数据流

| 文件 | 职责 |
|---|---|
| `manifest.json` | MV3 清单。两段 content script：`content.js`（ISOLATED / `document_start` / all_frames）+ `page-fill.js`（**MAIN** / `document_idle` / all_frames）；权限 `tabs/scripting/storage/alarms/declarativeNetRequest` |
| `background.js` | ① **发车填表**：`depFillFunc` + `fillByExecute()`（executeScript 注入）；② 目标标签页选取与回执；③ 地图 token 代理（绕 CORS / Referer）；④ 工具栏图标状态；⑤ `reloadReport` 刷新报表页 |
| `content.js` | ISOLATED world 消息桥：页面 `postMessage` ↔ `chrome.runtime`。**只转发，不碰页面逻辑** |
| `page-fill.js` | MAIN world 常驻：**车次列表回传**、地图 token 落地、**后备填表**（与 `depFillFunc` 同一套定位逻辑） |
| `popup.html / popup.js` | 配置界面：报表地址、**广播兜底开关**、地图 token 测试与注入、主题 |
| `rules.json` | DNR 规则：给地图后端接口补 CORS 响应头 / Referer |
| `安装说明.md` | 安装步骤与**排查手册** |

### 数据流（发车填表）

```
[计算器页] 点「发送」
   │  window.postMessage({channel:'__DEP_BRIDGE__', type:'fillByStrategy', cells, strategy})
   ▼
[content.js · ISOLATED]  转发
   │  chrome.runtime.sendMessage
   ▼
[background.js]  选目标标签页（精确匹配 → 广播兜底）
   │  chrome.scripting.executeScript({tabId, allFrames, world:'MAIN', func:depFillFunc, args})
   ▼
[报表页各 frame · MAIN]  depFillFunc 执行
   │  ①self ②找 iframe ③本帧兜底  →  contentPane.setCellValue(id, null, val)
   ▼
[background.js]  取 ok 最大的 frame 结果
   │  tabs.sendMessage → content.js → window.postMessage
   ▼
[计算器页]  成功优先 + 窗口聚合 → 状态栏提示「X道 编好」
```

| 日志 | 含义 / 处理 |

## 九、可复用的经验

1. **注入 > 转发**：扩展与页面通信，能"一次注入拿返回值"就别搭多跳消息链——跳数越多，静默失败越难查。
2. **让每个执行单元自判角色**：`allFrames` 注入 + 每帧自答"我能不能干"，比在顶层猜结构稳得多。
3. **不要用 DOM 伪造数据**：对"会被提交/校验"的数据，必须走官方运行时 API；DOM 降级只会制造"看起来成功"的假象。
4. **回执要设计去重/优先级**：多执行单元并发回执时，必须定义"谁的结果算数"。
5. **日志里带上身份**：把 `location.href` / frame 角色打进日志，能省掉大量排查时间（坑 5 就是靠它破的）。
